Documentation is a product surface. It helps humans use facts that already have
a machine authority, instead of becoming a second registry for those facts.

## One source tree

Product and engineering prose lives once under `docs/` and is rendered directly
by Starlight. The `docsite/` directory is only the build shell. Do not add
product documentation, custom navigation, search code, or hand-authored routes
under `docsite/`.

## Reuse before adding

Before writing a new page, check whether OpenAPI, Clap help, Mitase, the
capability report, or an existing repository check already answers the question.
Link to that authority instead of copying endpoints, flags, schemas, or
requirement graphs into prose.

## Link before duplicating

CLI detail belongs to `ugoite <command> --help`. REST detail belongs to
`crates/ugoite-server` and `/openapi.json`. Requirements belong to Mitase.
Docsite pages explain outcomes, prerequisites, steps, verification, what became
durable, and what to do when it fails.

## Static check before E2E

Prefer fast static checks for documentation structure: frontmatter validity,
relative link resolution, and link-rewrite behavior. Product behavior belongs in
product tests. Do not add runtime-backed product E2E for a typo or a navigation
change.

## Native before custom

Prefer Starlight tabs, badges, asides, and autogenerated navigation over custom
components, navigation engines, search engines, or frontmatter schemas.
Directory layout plus standard frontmatter ordering answers most information
design questions.

## Current and future stay apart

Current docs describe what ships. Planned pages carry a Planned badge. Larger
Current, Next, and North Star boundaries live in
[Current Product and Target State](../vision/current-and-target.md). Do not mix
future capability into current task pages.
