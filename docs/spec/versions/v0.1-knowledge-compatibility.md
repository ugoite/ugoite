---
title: "v0.1 Knowledge compatibility floor"
---

**Status:** required for the v0.1 Foundation Freeze

This is the compatibility contract for the Knowledge that v0.1 establishes.
Any later Ugoite version must be able to open a v0.1 Space and recover the
same Knowledge meaning from the operator-owned Space prefix. This promise is
about recoverability and authority; it does not freeze every implementation
detail or claim that future features are already shipped.

## Semantic contract

Later versions preserve these semantics:

1. **Ownership and portability.** The Space prefix is the move and recovery
   unit. Entries, Forms, Assets, saved SQL, Changes, and their durable history
   remain recoverable from operator-controlled storage without a hidden server
   database. Node control state and runtime state remain separate from the
   portable Space.
2. **Authority.** One current catalog authority determines the current state.
   In v0.1 that authority is the Catalog Head and the immutable publication
   chain reachable from it. Object listing, indexes, caches, SQL sessions,
   DerivedRelation Heads, browser state, and model context never establish
   current state or publication order.
3. **History.** Knowledge publications and Change history remain append-only.
   Past values are not silently rewritten, current state remains derivable from
   authoritative history, and selective Undo creates a new publication rather
   than rewinding the authority. Run IDs remain correlation metadata rather
   than a second durable history authority.
4. **Adapter boundaries.** CLI, REST, browser, MCP, WASM, and Konase operate on
   the same Knowledge semantics. Work, Experience, model providers, and
   transport adapters do not become Knowledge owners or introduce a parallel
   authorization/history authority.

These are semantic invariants, not a promise that a particular JSON object,
crate API, or UI component will remain unchanged.

## Versioned semantic surfaces

MCP v1 is a separately versioned semantic surface. Its deliberately narrow
tool, resource, authentication, and untrusted-content contracts may evolve by
introducing a later MCP version and an explicit compatibility decision. MCP v1
does not freeze the Space's physical storage encoding, and a storage refactor
does not silently change the meaning of an MCP v1 operation.

The same separation applies to other explicitly versioned protocol contracts.
An implementation API is not versioned merely because it is public inside the
repository.

## Not frozen by this contract

The following are current implementation details and may change in a separately
reviewed evolution:

- the physical encoding or file name of the current catalog authority,
  including the current `_ugoite/catalog/head.json` representation;
- Iceberg metadata, manifest, Parquet, and publication-object filenames or
  layout details that are not part of the semantic contract;
- Rust crate APIs, frontend component APIs, adapter internals, and generated
  build artifacts.

The current pre-release Space layout remains intentionally destructive: old
layouts are rejected rather than read through migration flags or compatibility
readers. A future physical replacement must provide its own explicitly scoped
reader/re-encoding work before it is presented as a supported evolution. That
future work must preserve this semantic contract and is not implied by v0.1.

## Canonical fixture

The repository keeps a small canonical semantic fixture at
`crates/ugoite-iceberg/tests/fixtures/v0.1-knowledge.json`. It records stable
Knowledge inputs and expected semantic observations, not a byte-for-byte copy
of Iceberg internals. The accompanying
`test_knowledge_compatibility.rs` test creates those inputs through the
authoritative path, closes and reopens the persisted Space prefix, resolves
the current and prior publications, and verifies current values and
append-only history through the reader path.

This fixture is the v0.1 compatibility oracle. It must remain readable and
semantically equivalent as storage encodings, crates, adapters, and UI evolve.
Changing the fixture requires an explicit versioned contract decision; it must
not be updated merely to make a regression pass.

## Compatibility review gate

Every pull request that can affect Space ownership, current-state authority,
publication reachability, history reconstruction, adapter authority, or the
canonical fixture must include a **Knowledge Compatibility Review**.

The review classifies the change as exactly one of:

- no effect on the v0.1 semantic contract;
- a preserving implementation change, with the fixture and relevant focused
  tests still passing. Its `Evidence:` note must be non-empty and must not
  retain the template placeholder; or
- a breaking semantic change, which cannot merge until an explicit review
  demonstrates how the v0.1 Knowledge meaning remains recoverable or a new
  versioned contract and migration/re-encoding scope has been approved. Its
  `Decision:` note must likewise be non-empty and must not retain the template
  placeholder.

The PR template and its required workflow gate carry this classification. A
review finding that does not make the change unsafe or impossible to merge is a
follow-up issue, not an excuse to weaken the compatibility contract.
