Saved SQL and SQL execution are separate concepts. A saved SQL definition is
durable Space Knowledge. `sql query` and `sql count` are disposable read
operations: they do not create a persistent execution session, result object, or other query
state in the Space.

## Outcome

You can either save a read-only SQL definition for later reuse, or execute a
stateless query page against the current authorized publication. The CLI uses
the same request contract in local and remote mode.

## Before you begin

Create an Entry in [Create and Edit Entries](entries.mdx) and confirm the Form
name with `ugoite form get`. Each Form is exposed as the backend-provided
`form_<FormId>` relation (the Form UUID without dashes, as returned in the
`id` field of `ugoite form get`) with `field_<FieldId>` columns plus
`_ugoite_id`, `_ugoite_created_at`, and `_ugoite_updated_at` columns. Entry
identity is `_ugoite_id`; human-readable labels are ordinary Form-defined
fields.

## Save a definition or run a query

<Tabs>
<TabItem label="Browser">

Use the SQL view to create or edit a saved SQL definition. Running a query is
read-only; saving the definition is the explicit Knowledge operation.

</TabItem>
<TabItem label="CLI">

```bash
# Durable SQL definition
ugoite sql saved-create \
  --name planning \
  --sql 'SELECT field_<FieldId> FROM form_<FormId> ORDER BY _ugoite_id'

# Stateless page query
ugoite sql query \
  'SELECT field_<FieldId> FROM form_<FormId> ORDER BY _ugoite_id' \
  --limit 100

# SQL from a file, with repeatable typed parameters
ugoite sql query query.sql \
  --param status=open \
  --param-type status=string \
  --format table

# Explicit count; count is not coupled to page retrieval
ugoite sql count \
  'SELECT field_<FieldId> FROM form_<FormId> WHERE field_<StatusId> = $status'
```

`sql saved-*` manages durable definitions. `sql query` and `sql count` accept
only one read-only `SELECT` statement and reject DDL, DML, and multiple
statements before execution. Use `ugoite sql --help` for the complete option
grammar.

</TabItem>
</Tabs>

## Read a result page

`sql query` returns a stateless page envelope:

```json
{
  "columns": ["field_<FieldId>"],
  "rows": [{"field_<FieldId>": "Alpha"}],
  "has_more": true,
  "next": "<opaque-continuation>"
}
```

When `has_more` is true, pass `next` back as `--continuation`. The
continuation fixes the publication used by the query chain while the current
authorization is checked again for every request.

An explicit `ORDER BY` is required for a result that needs more than one page.
An unordered result that exceeds `--limit` is rejected instead of silently
discarding rows; a single-page unordered result remains valid.

```bash
ugoite sql query \
  'SELECT field_<FieldId> FROM form_<FormId> ORDER BY _ugoite_id' \
  --limit 100 \
  --continuation '<opaque-continuation>'
```

The default JSON output preserves the complete page envelope. `--format
table` renders rows for humans and prints only a generic pagination notice to
stderr when another page exists. `--format ndjson` writes one row per line and
keeps pagination metadata out of the row stream. Use JSON output when a
continuation token is needed; opaque continuation values are never written to
logs by table or NDJSON rendering.

`sql count` returns a separate response:

```json
{"count": 42}
```

It is an explicit operation and is not executed automatically for each page.

## Parameters

Repeat `--param NAME=VALUE` for each named parameter. Scalar JSON values are
accepted; unquoted values that are not valid JSON are treated as strings.
Use `--param-type NAME=TYPE` when a null value needs an explicit type or when
the inferred scalar type is not the intended SQL type.

## Read-only and authorization contract

Only authorized public Form relations and their public columns are registered
for execution. Internal catalog, object-store, authorization, maintenance,
and derived-relation metadata are not automatically exposed to SQL. Query
execution is fixed-publication and read-only: it does not publish Knowledge,
materialize a result relation, or create persistent execution state.

## Saved SQL versus query execution

- Saved SQL is Knowledge and is managed with `sql saved-list`, `saved-create`,
  `saved-get`, `saved-update`, and `saved-delete`.
- `sql query` is a stateless page read with an opaque client-held
  continuation.
- `sql count` is a separate explicit read.

## If it fails

- SQL rejected: check the `form_<FormId>` relation, `field_<FieldId>` columns,
  and statement kind; only authorized read-only selects run.
- Parameter rejected: check `NAME=VALUE` syntax and add `--param-type` for
  null or an explicitly typed scalar.
- Continuation rejected: start a fresh query when SQL, parameters, or current
  authorization no longer match the continuation.
