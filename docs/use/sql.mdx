Saved SQL definitions are durable Space content. Sessions, indexes, and result
previews are derived and replaceable. Every execution path is read-only:
write and DDL input is rejected before execution.

## Outcome

A saved read-only definition exists in the Space and an expert query reads
the same Form data on Browser and CLI.

## Before you begin

Create an Entry in [Create and Edit Entries](entries.mdx) and confirm the
Form name with `ugoite form get`. Each Form is exposed as the
backend-provided `form_<FormId>` relation (the Form UUID without dashes, as
returned in the `id` field of `ugoite form get`) with `field_<FieldId>`
columns plus `_ugoite_id`, `_ugoite_created_at`, and `_ugoite_updated_at`
columns. Entry identity is `_ugoite_id`; human-readable labels are ordinary
Form-defined fields.

## Steps

<Tabs>
<TabItem label="Browser">

1. Open **SQL** for a saved definition over the same Form used in
   [Search and Filter](search.mdx).
2. Save the definition so it reopens with identical text.
3. Run it and confirm the same Form rows appear.

</TabItem>
<TabItem label="CLI">

```bash
ugoite sql lint 'SELECT _ugoite_id, field_<FieldId> FROM form_<FormId> LIMIT 10'
ugoite sql saved-list
ugoite sql saved-create \
  --name planning --sql 'SELECT _ugoite_id FROM form_<FormId> LIMIT 10'
ugoite sql saved-get <sql-id>
ugoite sql saved-execute <sql-id> --limit 20
ugoite query \
  --sql 'SELECT _ugoite_id, field_<FieldId> FROM form_<FormId> LIMIT 10'
```

`sql lint` checks syntax only; it does not resolve Forms or authorize
execution. `sql saved-*` manages durable definitions; `sql session-create`,
`sql session-get`, `sql session-count`, and `sql session-rows` page one
bounded read-only result set. `query` is read-only and rejects DDL and DML
without changing the Space. Take `<sql-id>` from `sql saved-list` output.
Run `ugoite sql --help` and `ugoite query --help` for exact flags.

</TabItem>
</Tabs>

## Read a result page

`sql session-create` returns the session handle; `sql session-count` and
`sql session-rows` read from it. Sessions are throwaway pagination state,
not durable Knowledge.

```bash
ugoite sql session-create \
  --sql 'SELECT _ugoite_id, field_<FieldId> FROM form_<FormId> ORDER BY _ugoite_id'
```

```json
{
  "id": "<session-id>",
  "pagination": {
    "default_limit": 50,
    "max_limit": 1000,
    "max_offset": 999,
    "strategy": "offset"
  },
  "space_id": "<space-id>",
  "sql": "SELECT _ugoite_id, field_<FieldId> FROM form_<FormId> ORDER BY _ugoite_id",
  "status": "ready"
}
```

`sql session-count` returns the total row count for the session:

```bash
ugoite sql session-count <session-id>
```

```json
{
  "count": 2,
  "session_id": "<session-id>",
  "total_count": 2
}
```

`sql session-rows` returns one bounded page. Every row page carries the
same envelope: `rows` (this page), `count`
(rows in this page), `total_count` (rows in the whole result), `offset`,
and `limit`, plus the `session_id` continuation handle. Pages default to
`--limit 50`; `--offset`/`--limit` must stay within the `max_limit` window
above.

```bash
ugoite sql session-rows <session-id> --offset 0 --limit 1
```

```json
{
  "count": 1,
  "limit": 1,
  "offset": 0,
  "rows": [{ "_ugoite_id": "task-a", "field_<FieldId>": "Alpha" }],
  "session_id": "<session-id>",
  "total_count": 2
}
```

`sql saved-execute` returns the same page envelope with `sql_id` for the
executed definition. Local/core mode carries no `session_id`:

```bash
ugoite sql saved-execute <sql-id> --limit 1
```

```json
{
  "count": 1,
  "limit": 1,
  "offset": 0,
  "rows": [{ "_ugoite_id": "task-a", "field_<FieldId>": "Alpha" }],
  "sql_id": "<sql-id>",
  "total_count": 2
}
```

Remote mode (CLI pointed at a server) returns the same envelope plus a
`session_id` continuation handle:

```bash
ugoite sql saved-execute <sql-id> --limit 1
```

```json
{
  "count": 1,
  "limit": 1,
  "offset": 0,
  "rows": [{ "_ugoite_id": "task-a", "field_<FieldId>": "Alpha" }],
  "session_id": "<session-id>",
  "sql_id": "<sql-id>",
  "total_count": 2
}
```

Contract notes:

- `sql_id` is the identity of the saved SQL definition (durable Knowledge).
- `session_id` is a transient handle for the remote SQL execution/session,
  used for result continuation. It is runtime/transport metadata, not
  durable Knowledge.
- `session_id` is not guaranteed to be present in local/core mode. Scripts
  and automation must not require it, and must not treat its presence or
  value as Knowledge semantics.
- Row, count, and pagination meanings (`rows`/`count`/
  `total_count`/`offset`/`limit`) are identical across both transports.

## Verify the result

The saved definition reads back with identical text, and the expert query
returns the same Form rows that the Browser SQL view shows.

## What became durable?

The saved SQL definition. Sessions, result pages, and previews are derived
runtime state.

## If it fails

- SQL rejected: check the `form_<FormId>` relation, `field_<FieldId>` columns,
  and statement kind; only read-only selects over authorized relations run.
- Unknown saved ID: list definitions again and use the exact ID from
  `sql saved-list` output.
