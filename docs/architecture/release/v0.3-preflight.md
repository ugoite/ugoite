This page records the v0.3 preflight boundary. It is a navigation and decision
record, not a new product specification or release completion claim. The
generated report is a static projection of existing authorities; Mitase checks
declared relationships and evidence but does not run Ugoite tests or certify
product intent.

## Reproduce the projection

Run from the repository root:

```sh
mise exec -- deno run -A tools/capability_report.ts --scope v0.3-preflight --json
mise exec -- deno run -A tools/capability_report.ts --scope v0.3-preflight --markdown
```

The existing Golden Journey scope is unchanged:

```sh
mise exec -- deno run -A tools/capability_report.ts --json
mise exec -- deno run -A tools/capability_report.ts --markdown
```

The investigation plan identifies `74777bbdc8a609277d6adf87caaed3fcd2f669ef`
as its source snapshot. The PRE-01 implementation started from `origin/main`
at `bf1f99bab96d34bc423c2918b4ee7b8950f56e46`; these are separate facts. The
projection reads the checked-out source and must be regenerated for the commit
being reviewed. Its `source-located` status does not mean a test was run. Only
an independently recorded run tied to a command, source SHA, and result URL can
support `executed-and-passed`; this tool never emits that status.

## Read the report

The inventory contains one row for each preflight capability, with operations
or Host/resource pointers, Requirement/Criterion references, Feature Binding
references, source paths, surface observations, verification claims, test
selectors, availability, evidence status, reason, and follow-up issue. JSON and
Markdown are rendered from the same report object. Missing references or
artifacts remain visible as unresolved or missing evidence.

`availability` and `evidence_status` are independent. Availability describes
whether the capability exists or needs surface work. Evidence status describes
whether a declaration or source was located, whether evidence is missing, or
whether execution was not recorded. In particular, `existing` does not mean
every UI flow is complete, and a source path does not prove its behavior.
Each surface observation names its own source paths, so CLI core and CLI remote
do not inherit the same undifferentiated evidence list. These paths remain
static locators, not runtime reachability or authorization proofs.

The portable TypeScript and Rust manifests must match in content and order. That
static equality is distinct from operation reachability, authorization, MCP
Host behavior, WASM behavior, and E2E results. The read-only `ugoite://form/{id}`
resource is not a Form save operation. `ugoite.save` and `ugoite.delete` are MCP
facade tools, not invented portable REST operations. Remote `space.create`
remains intentionally outside the CLI path because setup requires the recent
Passkey and node-admin Browser ceremony documented in C3.

## Authority map and design gate

[`docs/spec/migration.md`](../../spec/migration.md#cross-surface-preflight-authority-map)
lists the canonical and partial sources by domain. No Requirement was narrowed
or created solely to fill this projection. The selected-Context admission and
one-shot write-approval Criteria now fill the previously explicit Konase Host
gaps in the canonical Mitase graph; the Feature binding points to their
portable and Host artifacts.

Application Definition design may be considered after [#3120](https://github.com/ugoite/ugoite/issues/3120)
and [#3157](https://github.com/ugoite/ugoite/issues/3157) meet their exit
conditions, the preflight map can trace the existing EntryQuery, SQL, Form, and
Mutation boundaries, and no unexplained authorization or semantic-drift gap
remains. PRE-01 completion alone is not that decision. The saved representation,
Capability granularity, QueryHandle, Saved SQL's formal Konase read path, and
durable background Work stay open design questions.
